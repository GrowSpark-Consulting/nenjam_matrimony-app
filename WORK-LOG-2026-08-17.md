# Work log — 17 August 2026

Session record: a full read-only performance audit of the Flutter frontend,
followed by two implementation phases against its findings — deterministic
startup/image/debug fixes (Phase 1), then web media enablement, startup
parallelisation, request cancellation and a targeted rebuild fix (Phase 2).

Written to be useful to someone who wasn't here — including the things that are
**not** done, and the places where the audit itself turned out to be wrong.

Branch: `feat/production-backend-hardening`. No backend code was modified.

## 2. Phase 1 — deterministic fixes

Net **−97 lines** across 27 files. Deletion-heavy by design.

| Change | Detail |
|---|---|
| Splash floor removed | `_startUp()` now awaits only the health probe. `/health` check, error state and Retry preserved. No replacement minimum added. |
| Debug instrumentation stripped | All 18 unguarded sites plus `_DebugNavObserver` (×5), `_dumpAllNavigatorPages`, the `FlutterError.onError` wrapper, `debugLogDiagnostics`, `_LoggingBackButtonDispatcher`; `routerConfig: router` restored. −140 lines in `app_router.dart` alone. |
| Image decode sized | New `NmSizedNetworkPhoto` reads real constraints via `LayoutBuilder`, derives `cacheWidth` from longest edge × DPR, capped at the 1080 source. 12 call sites. |
| Duplicate draft fetch fixed | `profileDraftResponseProvider` was `autoDispose` with inherently transient consumers → refetched on every drawer open. Now session-scoped; 4 explicit `invalidate` sites preserve freshness. |
| Web crash guarded | `AttachmentPicker.pick()` — the single chokepoint for all three media flows — guarded with `kIsWeb`. |

### Decode arithmetic (dpr 3, source 1080²)

Not measured memory — arithmetic from decode dimensions.

```
Avatar                32 dp →   96 px    0.04 MB   99.2% less
Story ring            76 dp →  228 px    0.20 MB   95.5% less
Photo manager thumb  160 dp →  480 px    0.88 MB   80.2% less
Recently Joined      192 dp →  576 px    1.27 MB   71.6% less

Premium card         260 dp →  780 px    2.32 MB   47.8% less
```

The win concentrates on small elements. Full-bleed surfaces legitimately need
the full source and were left alone.

### The audit recommendation that was wrong

The audit called for migrating all 18 image sites to `CachedNetworkImage`.
**Reading the code showed that would be actively harmful.** `UserPhoto.cdnUrl`
is documented in source as *"a short-lived **presigned** GET URL (the bucket is
private), so it must not be persisted or cached long-term."* A URL-keyed disk
cache would never hit (the signature changes every fetch), would fill the disk
with expired entries, and would persist private-bucket content. Not
implemented. Download cost needs stable URLs from the backend first.

Also corrected: "28 debugPrints in release" was imprecise. 28 was the total;
only 18 were unguarded. The other 10 are `kDebugMode`-gated and were kept.

## 3. Phase 2 — web media, startup, cancellation, rebuilds

55 files, **+437 / −363**.

### 3.1 Web media — made functional, not faked

The chain was `File`-typed end to end. Currency moved to **`XFile`** — already
what `image_picker` returns, already a transitive dependency, so no new
abstraction was invented.

```
AttachmentPicker  → XFile          (no longer unwraps to a path)
CropService       → XFile
PhotoCropScreen   → XFile in/out   (readAsBytes works on both platforms)
ImageCompressor   → Uint8List      (no filesystem at all)
Repositories      → MultipartFile.fromBytes   (was fromFile — dart:io only)
```

`dart:io` now appears in exactly **one** file, `local_media_image_io.dart`,
behind a conditional import. Verified absent from the built web bundle.

| Flow | Web status |
|---|---|
| Profile photo select → crop → compress → upload | **Functional** |
| Chat image attachment | **Functional** |
| Verification document upload | Client ready — **backend is a 4-line stub**, no route exists on any platform |
| Voice messages | **Not supported**, degrades to a localized message |

### The second audit correction

The audit stated the chat attachment endpoint did not exist. That repeated a
stale comment in `api_endpoints.dart`. Checking the backend found
`chat/controllers/attachments.controller.ts` is real (`POST /chat/attachments`,
`FileInterceptor`) — so chat image upload *was* achievable, and now works.
Verification really is a stub (`verification.controller.ts` is 4 lines), so it
was not faked.

### 3.2 Startup

```
WidgetsFlutterBinding.ensureInitialized()
        ↓
  ┌─────┴──────┬──────────────┬──────────────┐   ← all four independent
orientation  Firebase      AppConfig      storage
  └─────┬──────┴──────────────┴──────────────┘
        ↓
FirebaseMessaging.onBackgroundMessage()   ← must follow Firebase
        ↓
runApp()
```

Failure behaviour is unchanged — previously any throw aborted `main()`, and
`Future.wait` propagates the first error identically. The orientation lock
stayed *inside* the barrier so the first frame can never paint landscape then
snap. Auth work was not moved; route protection untouched.

**Incidental finding:** `AppConfig` is initialised at startup and then **never
read anywhere** — `envConfig` has zero consumers outside `main.dart` and the
dead `bootstrap.dart`. Left in place (out of scope), but noted.

`StoryPerf` marks added at: `main()` entry, init complete, `runApp`, first
frame, health probe resolved, initial route resolved. All `kDebugMode`-gated.

### 3.3 Request cancellation

Traced every `autoDispose` provider. Only **three** actually reach the network:

| Wired | Not wired — and why |
|---|---|
| `mySettingsProvider` | `myTrustScoreProvider` — unavailable stub |
| `myTicketsProvider` | `profileDetailProvider` — mock datasource |
| `promptBankProvider`, `myPromptsProvider` | personality / compatibility — mock repos |
| | `profileCompletenessSnapshotProvider` — derived, no request |

**Search needs no cancellation.** It issues zero API calls — the 350ms debounce
feeds a synchronous filter over the already-loaded feed. Nothing is in flight.
Debounce untouched.

Session-scoped providers (discover, photos, notifications, interests,
shortlist, conversations) deliberately **not** cancelled — their results are
still wanted after navigation.

### 3.4 Rebuilds — and why no model got `operator ==`

The plan was "add equality where profiling shows it helps". Static analysis
showed equality was **the wrong tool** for the confirmed hotspot:

- `.select()` compares the *selected value*, not the model — so selecting an
  `int` or `bool` works with no equality on the parent.
- On a keystroke the draft genuinely changes, so `==` would suppress nothing.

`ProfileWizardPage` now watches two derived scalars instead of the whole draft:

```dart
final stepIndex   = ref.watch(registrationProvider.select((d) => d.currentStep));
final isStepValid = ref.watch(registrationProvider.select(_isCurrentStepValid));
```

The full draft is watched only by a `Consumer` around the step content. Per
keystroke, the `PopScope`, `LayoutBuilder`, journey header, motivation caption,
`AnimatedSwitcher` and sticky bottom bar no longer rebuild.

**Zero models were modified.**

Supporting evidence: only 6 `.select()` call sites exist app-wide, and **5 are
on `presenceProvider`** — the one model that *has* `operator ==`. That
correlation is the real link between missing equality and missing granularity.

### 3.5 Responsive — measured, then left alone

The shipped overflow suite covers phone widths only (≤480 portrait). It was
temporarily extended to tablet/desktop widths as a throwaway probe.

**Result: all 8 screens pass at 600 / 768 / 834 / 1024 / 1280 / 1920 px**, both
locales, both orientations, with safe-area insets — zero RenderFlex overflows.

So there is **no critical layout bug**, and no layout was changed. The
responsive problem is layout *quality* (stretched phone UI, over-wide cards,
long line lengths), not correctness. Probe removed after the run.

Highest hardcoded-pixel density: registration (237), discover (71), inbox (62),
profile_detail (33).

- **iOS is unverified and push is still broken** — no Podfile, no
  `Runner.entitlements` (so no `aps-environment`), no `UIBackgroundModes`.
  Needs a Mac.
- **Verification upload has no backend route.** `verification.controller.ts`
  is 4 lines. The client is ready; the server is not.
- **Voice messages do not work on web** — `getTemporaryDirectory()` has no web
  implementation and the upload leg is the one remaining
  `MultipartFile.fromFile`. Guarded, not fixed.
- **No browser testing.** Chrome/Edge/Safari/Firefox behaviour is unverified;
  the web media work is confirmed by code and build, not by running it.
- **No device profiling.** Every runtime performance claim remains unmeasured.
- Responsive layout quality at tablet/desktop; `AppTheme.light`/`.dark` still
  getters; Google Fonts still fetched at runtime (3 families); no deferred
  loading (2 MB single JS bundle); `ChatMediaImage` still uncapped;
  `ScreenUtil` initialised but unused; `AssetPaths` and `bootstrap.dart` still
  dead; placeholder `applicationId` (`com.example.nenjam_matrimony`).

## 6. Risks carried forward

- **The media migration is the largest risk.** It touches upload contracts
  across three features. Analyzer and tests pass, but upload has not been
  exercised against a live backend on any platform. Worth a manual Android
  pass before merge.
- `MultipartFile.fromBytes` reads the whole file into memory where `fromFile`
  streamed. Negligible for ~150–300 KB JPEGs, but it is a change in mechanics.
- Chat image retry re-wraps `attachmentUrl` in `XFile`; on web that `blob:` URL
  is valid only while the page lives, so retry after a reload will fail.
- The splash is now visibly shorter and its 1,500 ms animation may be cut off
  when startup is fast. Animation deliberately left untouched.
- `compute()` has no isolate on web, so the JPEG encode runs on the main thread
  there — a one-off cost on crop confirm.
