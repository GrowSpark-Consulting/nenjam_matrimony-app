## 2. Security remediation

**`backend/.env.example` — which git tracks — contained live credentials**
(Neon password, Firebase private key, AWS keys, Elasticsearch password). It is
the single `!.env.example` exception in `.gitignore`, so the next `git add -A`
would have published them.

### History audit

Scanned all 121 commits across every local and remote branch. **No live
credential has ever been committed.** Two apparent hits were false positives:

- `.env.example` @ `c504466` — the private key is literally
  `-----BEGIN PRIVATE KEY-----\nCHANGEME\n-----END PRIVATE KEY-----`
- three `*.spec.ts` files — test fixtures using `\nMOCKKEY\n`

One **real but low-impact** exposure: `backend/.env` was committed in 5 commits
(6–9 Jul, on `origin/main`) containing `DATABASE_URL`, `DATABASE_PASSWORD` and
`JWT_SECRET`. The database URL pointed at **`localhost`**, so those are local
dev credentials. The two old JWT secrets differ from the current one.

### Actions

- Sanitised `backend/.env.example` — 36 variables, same names, placeholders
  only, with comments explaining each and the either/or relationships
  (`DATABASE_URL` vs discrete `DATABASE_*`; `REDIS_URL` vs discrete `REDIS_*`).
- Verified `.gitignore` with `git check-ignore -v` (resolved outcomes, not
  pattern-reading). All required paths ignored; `.env.example` trackable.
- Added **`scripts/git-hooks/pre-commit`** — a dependency-free secret guard.

### The pre-commit hook

Chosen over gitleaks to avoid pinning a third-party binary; ~130 lines of
auditable shell that works offline.

Scans **staged additions only**. Two layers: file-level (real env files,
service-account JSON, keys/keystores — covering the `git add -f` and
tracked-before-ignored gaps `.gitignore` can't) and content-level (AWS keys,
PEM keys with real material, Postgres/Redis/Mongo URLs with inline passwords,
Neon `npg_`, Google API keys, GitHub/Stripe/Slack tokens, JWTs, Resend keys).

Exempts placeholder values and public-by-design Firebase client config.
Patterns target structured, high-entropy credentials on purpose — a rule that
fires on the word "password" just trains people to reflexively `--no-verify`.

Install is automatic via `backend`'s `prepare` script; manually:

```bash
git config core.hooksPath scripts/git-hooks
```

**Two bugs were found by testing it**, which is the argument for testing a
security control rather than shipping it:

1. Patterns beginning with `-` (the PEM header) were parsed by grep as flags,
   so that rule silently never ran. Fixed with `grep -e`.
2. The hook blocked its own commit — its source necessarily contains every
   pattern it looks for. Fixed by skipping its own directory for content rules
   (file-level rules still apply), **not** by using `--no-verify`.

## 3. Transactional email system

```
MailService  ->  BullMQ (Redis)  ->  worker EmailProcessor  ->  EmailProvider
```

Business logic never touches Resend. Callers name an `EmailType`; the
`EMAIL_PROVIDER` token resolves the vendor.

### `libs/queue` — implemented for real

It was empty scaffolding: `QUEUE_NAMES` was `{}`, `QueueModule` was
`@Module({})`, all 7 processors and producers were `// TODO` stubs, and BullMQ
wasn't installed. Email is its first consumer; the other stubs now have a
foundation.

**BullMQ cannot share the cache Redis client.** That client sets
`maxRetriesPerRequest: 1` so a blip fails an HTTP request fast; BullMQ's workers
hold blocking reads and throw unless it is `null`. Separate connection to the
same instance.

### `libs/mail`

12 `EmailType`s → 13 Handlebars templates (12 + shared layout). Table-based,
600px, mobile media queries, inline styles, bulletproof CTAs, logo placeholder
with wordmark fallback. Brand colours match `Frontend/lib/core/theme/app_colors.dart`
(navy `#1B2B4B`, gold `#C9A84C`).

| Piece | File |
|---|---|
| Business API | `libs/mail/src/mail.service.ts` |
| Provider contract + DI token | `providers/email-provider.interface.ts` |
| Resend implementation | `providers/resend.provider.ts` |
| No-op fallback | `providers/noop.provider.ts` |
| Producer | `queue/email.queue.ts` |
| Worker consumer | `queue/email.processor.ts` |
| Handlebars + HTML→text | `template.renderer.ts` |
| Persistence | `repository/email-log.repository.ts` |

`MailModule.forRoot()` = producer (API, scheduler); `forWorker()` adds the
processor, renderer and provider. Otherwise every API replica would also
consume, multiplying concurrency by replica count.

**Queue policy:** 5 attempts, exponential backoff 5s→80s, concurrency 5
(`MAIL_QUEUE_CONCURRENCY`), 4 priority tiers (OTP=1 … digest=4), delay + dedupe,
`removeOnComplete` 24h / `removeOnFail` 7d.

**Dead-lettering, precisely:** there is **no separate DLQ queue**. Exhausted
jobs live in BullMQ's `failed` set (7-day retention) plus an `EmailLog` row at
status `DEAD_LETTER`. Recoverable, but not a queue — an earlier description of
this as "DLQ" overstated it.

### Design decisions worth knowing

- **`RESEND_API_KEY` is optional**, matching how Firebase and AWS already behave
  here. Without it a no-op provider is bound: queue, worker, render and
  `EmailLog` write all still run; only the HTTP call is skipped. Requiring it
  would block every developer and CI run on a third-party secret. Format *is*
  validated when present.
- **Quota errors are non-retryable.** `daily_quota_exceeded` resolves over
  hours; the backoff ladder spans ~80s. Retrying burns all 5 attempts to reach
  the same conclusion, so it dead-letters immediately for later replay.
- **Subjects are not HTML-escaped.** A subject is a mail header, not markup —
  escaping turns `O'Brien` into `O&#x27;Brien` in the inbox list. The real
  threat, header injection, is handled by stripping CR/LF.

## 4. Prisma migration drift — two instances

### Instance 1: `20260724120000_add_user_settings`

Applied to the shared Neon database from a developer machine, **never committed
to any branch**. Consequences:

- `prisma migrate dev` demanded a **full reset of the shared database**
- the auto-generated diff contained `DROP TABLE "user_settings"` (1 live row)
  and `DROP TYPE "theme_mode"`

Used `--create-only` and hand-wrote an additive-only migration. Reconstructed
SQL is **byte-identical** to the recorded checksum. Per decision, the table was
**adopted** into `schema.prisma` (`UserSettings` + `ThemeMode`) rather than
dropped — `theme`, `push_notifications_enabled` and `language` exist nowhere
else, so it may be a paused feature rather than dead code.

### Instance 2: `20260803120000_add_chat_message_reply`

Appeared **mid-session** — applied to Neon at 11:12 UTC by a teammate while
this work was in progress. Deliberately left untouched; "fixing" it would have
dropped their column and 2 rows of data. They later pushed it, and its checksum
matched byte-for-byte.

### Final state

```
19 migration folders on disk = 19 applied in Neon
0 pending · 0 orphaned · 0 checksum mismatches
migrate diff → "No difference detected."
```

### Two lessons

1. **`prisma migrate status` cannot detect a database ahead of the repository.**
   It reported "Database schema is up to date!" in both instances. Use
   `migrate diff --from-config-datasource --to-schema`.
2. **The root cause is process, not schema.** Two occurrences in ten days from
   two developers. Until migrations are applied only from CI — or the shared
   database stops being a `migrate dev` target — this recurs.

## 5. Workflow wiring

All enqueued **after** the transaction commits, via `EmailDispatchService`
(a sibling of the existing `PushDispatchService`, same never-throws contract).

| Workflow | Trigger | Behaviour |
|---|---|---|
| Welcome | `ProfileService.finalize()` | after every write commits |
| Match found | `InterestsService.respond(accept=true)` | acceptance only — no email on decline |
| New message | `MessagesService.send()` | **only when the recipient is offline** |
| Weekly digest | new `WeeklyDigestCron` | per-week dedupe key; skips members with no candidates |

The new-message email gates on `presence.isOnline` — a value `send()` already
computes, so zero extra queries. Media messages send no preview: their content
is a signed S3 URL that expires long before the email is read.

The digest also required **activating the scheduler app** — `@nestjs/schedule`
wasn't installed and all four crons were 2-line stubs.

### Not wired — no trigger point exists

- **OTP, forgot-password, email-verification** — Firebase Auth owns all three;
  the backend has zero code for them. Wiring our own would create a second,
  competing auth path. (`/auth/*` returns 404; those Flutter constants are dead.)
- **Subscription emails** — `checkout.service.ts`, `razorpay.service.ts` and
  `razorpay-webhook.controller.ts` are 4 lines each.
- **Profile viewed** — the `ProfileView` table exists but **nothing writes to
  it**.

The `MailService` methods for these exist and are tested, awaiting the features.

## 8. Outstanding — read before relying on any of this

### Blocking for email in production

1. **No live delivery has ever been confirmed.** `RESEND_API_KEY` is unset, so
   only the pipeline is proven. Set it and run:
   ```bash
   cd backend && pnpm verify:email you@example.com
   ```
   `onboarding@resend.dev` only delivers to the Resend account owner's own
   address — use a verified domain for real users.

2. **Redis eviction policy is `volatile-lru`; it should be `noeviction`.**
   BullMQ warns on every connect. Under memory pressure it can silently evict
   queued jobs — an OTP would simply vanish. Infrastructure change, not code.

### Recommended

3. **Add `tsc --noEmit` and an app-boot smoke test to CI.** This session found
   two type errors and one DI failure that the existing gates structurally
   cannot catch (`nest build` excludes specs and never runs DI; nothing starts
   the apps).

4. **Rotate the two old `JWT_SECRET`s** exposed in `origin/main` history, if
   anything still validates tokens signed with them.

5. **Fix the migration process** — see §4.

### Lower priority

6. 38 pre-existing lint errors in files this work didn't author. Mostly
   `no-unsafe-member-access` / `no-unnecessary-type-assertion` — **not**
   prettier-fixable, so `pnpm lint` won't clear them.
7. `Frontend/android/app/google-services.json` is tracked despite
   `.gitignore:47`. Not a leak (public client config), but decide deliberately.
8. Two junk files tracked at repo root (`-server`, one mojibake-named).
9. Windows Developer Mode is off — blocks the Flutter **Windows desktop** target
   only. Android and web build fine.
10. The weekly digest runs one query per user. Fine at current scale; needs
    batching later. It also doesn't reuse `ProgressiveFallbackStrategy` (that
    lives in `apps/api` and isn't importable from the scheduler).

### Switching Resend → AWS SES

Three steps; nothing above the interface changes:

1. Write `SesEmailProvider implements EmailProvider` — one method. Map
   `ThrottlingException`/`ServiceUnavailable` to `retryable: true`;
   `MessageRejected`/`MailFromDomainNotVerified` to `false`.
2. Add `case 'ses':` to the factory in `libs/mail/src/mail.module.ts` and widen
   the `provider` union in `configuration.ts`.
3. Set the env var.

`MailService`, `EmailQueue`, `EmailProcessor`, every caller, every template and
every test are untouched. `EmailLog.provider` is a plain string precisely so
this needs no migration.
