## 2. Commits

### `5d47238` — 8 Sep, 16:25 IST

**`feat(birthdate): manual DD/MM/YYYY entry with a 21-year minimum age`**
*35 files changed, +3,786 / −646*

- Three typed boxes replace the calendar picker on onboarding's Your Name step and in the Edit Profile wizard. A member entering a relative's date of birth no longer scrolls a picker back two decades.
- **One rule, three places.** `BirthDateInput` (Flutter) and `birth-date.ts` (NestJS) state the same table, and `NmBirthDateField` is the only DOB input in the app — so no screen can accept a date another screen, or the server, would reject.
- `@IsDateString()` on `BasicDetailsDto` had been accepting every impossible, future and under-age date the client was already refusing. It is now `@IsBirthDate()`, which re-checks all of it and returns a member-readable reason.
- **A date of birth is a calendar date, not a timestamp.** The wire format is now date-only `YYYY-MM-DD`. The previous write path parsed through `new Date()`, which read a zone-less `1998-08-15T00:00:00.000` as *local* midnight — on an IST server that stored, and read back, the 14th. Legacy ISO timestamps are still accepted (shipped clients send them, stored drafts hold them) but are normalised at the DTO before anything downstream sees them.
- Verified against the real database: **49 of 49** stored draft values still parse. No schema change — `user_profiles.dob` is already `timestamp(3) NOT NULL`.

### `c3a053e` — 9 Sep, 13:51 IST

**`feat(edit-profile): follow the registration flow, and score completion by field`**
*31 files changed, +2,510 / −420*

- Edit Profile asked a different set of questions than registration, in a different order, with free text where registration had lists. It now builds the **same step widgets in the same order** — one flow, one set of answers, rather than two that drift.
- **Dependent lists finally wired up:** religion drives community, country drives state, state drives city. Changing a parent clears a child the new parent cannot offer and *keeps* one it can, so re-picking the same country does not cost an answer that is still true.
- Every dropdown goes through `OnboardingScaffold.optionsWith`, so a stored value the curated list never carried (`Goa`, a community typed through "Other") stays selected instead of being blanked on save.
- **`college` gets its own column.** It had been folded into `education_details` via `joinNonEmpty(college, employmentType, workLocation)`, so once written it could not be read back out. `education_details` is untouched and still populated — nothing stored is lost.
- **`workIndustry` is genuinely new** and runs the whole way through: Flutter model, DTO, service, schema, migration, write path. Its option list is promoted out of `partner_preferences_page.dart` so the sector a member states and the sector they filter by come from one place.

#### Completion is now four slices, not ten

| Slice | Weight | Rule |
|---|---:|---|
| Registration information | 60 | `round(60 × answered / 21)` |
| About Family | 10 | unchanged |
| Horoscope / Astro | 5 | unchanged |
| Verification | 25 | unchanged |

A member who answered every registration question previously scored **20%**. Height, diet and the work fields belonged to modules demanding *more* than registration asks, so those modules sat at zero and the member was docked for fields nobody had asked them for. The seven absorbed weights sum to exactly 60.

The 21st item is a profile photo — onboarding lets a member skip it, and without it in the slice a photo-less profile could read 100%.

A field counts only when **meaningful**: "Other" is the dropdown placeholder and `OtherOptionField` stores `''` until a custom value is typed, so a literal "Other" reaching the server is an unanswered field. `dob` must additionally parse to a real day, but **the 21-year floor is deliberately not applied here** — two live members are under 21 and must not be told their profile is incomplete over a date they cannot change.

## 3. "Complete Your Profile" recommendation cards

Committed during this session. Frontend, backend, and one new table.

### What it does

Home (Discover) and Edit Profile both render a row of cards for the sections a member has not finished. A card can be dismissed with the cross, and **the dismissal is stored server-side** — it survives a restart, a re-login and a reinstall.

### The design decisions worth recording

- **A dismissal hides the suggestion, never the data.** `profile_recommendation_dismissals` holds one row per `(user_id, card_key)`, and no profile query reads that table. Deleting a row simply makes the card eligible again, with whatever the member had already saved still behind it. "I don't want to be asked about my horoscope" and "I have no horoscope details" are different statements, and the previous client-only dismissal could not tell them apart across a reinstall.
- **Every route returns the whole completion entity** — percentage, breakdown *and* cards — rather than just what changed. That is what keeps the two screens in step: whichever screen dismissed a card gets back the same authoritative state the other would have fetched, so there is no window in which they disagree.
- **This is not a second scoring model.** The percentage stays exactly where section 2 put it. A card is a suggestion built on a completion signal, which is why `psychology` appears with `affectsScore: false` and no weight — it is offered, never counted, and adding it moved no member's percentage.
- **`card_key` is plain `TEXT`, not an enum**, so adding a card never needs a migration. An unknown key read back is ignored by both sides rather than throwing.
- **Registration cards show *instead of* the section cards**, never alongside. A member who has not finished signing up is asked to finish signing up, not to fill in their horoscope.
- **Dismissal is optimistic.** The card leaves the row on tap (`pendingDismissals`), not on the round trip; a failed request puts it back and tells the member. The database stays the source of truth.

### Surface area

| Layer | Files |
|---|---|
| API routes | `GET /profiles/completion`, `POST /profiles/completion/dismissals`, `DELETE /profiles/completion/dismissals/:cardKey` |
| Backend | `controllers/profile-completion.controller.ts`, `domain/recommendation-cards.ts`, `repositories/recommendation-dismissal.repository.ts`, `dto/dismiss-recommendation.dto.ts`, `entities/profile-completion.entity.ts`, `services/profile-completion.service.ts` |
| Migration | `20260909130000_add_profile_recommendation_dismissals` |
| Flutter | `domain/completion_recommendation.dart`, `data/completion_recommendation_repository.dart`, `presentation/providers/completion_recommendation_provider.dart`, `presentation/widgets/complete_profile_section.dart`, `core/widgets/cards/completion_card.dart` |
| Wiring | `discover_page.dart`, `profile_review_page.dart`, `api_endpoints.dart` |
| Localisation | 17 new keys, **English and Tamil both complete** |

`ProfileCompletionService.calculate()` gains two reads on a hot path (every wizard "Continue" recomputes completion). Both are single-column and index-covered on `user_id`, and they are here rather than on a second endpoint precisely so the two screens cannot drift.

## 4. Android build environment — fixed

At the start of 9 Sep, `flutter run` failed after **14m 39s**:

```
Execution failed for JetifyTransform: ...arm64_v8a_debug-1.0.0-....jar
   > Java heap space
```

**Root cause.** `android.enableJetifier=true` made Gradle run the AndroidX-rewrite transform over every jar on the compile classpath — including Flutter's ~1 GB `arm64_v8a_debug` engine jar — and that exhausted the 2 GB daemon heap. **Nothing in this project needs Jetifier:** no dependency references `com.android.support` or `android.arch`. It was dead weight that happened to be expensive enough to kill the build.

`-XX:+HeapDumpOnOutOfMemoryError` then wrote a **1.59 GB** `java_pid13452.hprof` into `Frontend/android/` on each crash.

**Changes — `Frontend/android/gradle.properties`:**

| Setting | Before | After | Why |
|---|---|---|---|
| `android.enableJetifier` | `true` | `false` | The actual fix. Nothing needs it. |
| `org.gradle.jvmargs` | `-Xmx2G`, metaspace 512m | `-Xmx4G`, metaspace 1G | 2 GB was not enough for AGP 8 + Kotlin 2.2. |
| `kotlin.daemon.jvmargs` | *(unset)* | `-Xmx2G` | The Kotlin compile daemon is a **separate JVM** and does not inherit `org.gradle.jvmargs`; it could OOM independently. |
| `-XX:+HeapDumpOnOutOfMemoryError` | set | removed | Wrote a heap-sized dump into the source tree on every OOM. |

`*.hprof` added to `Frontend/.gitignore`; the existing 1.59 GB dump deleted.

**One course correction, recorded so it is not undone.** `org.gradle.parallel` and `org.gradle.caching` were tried and **removed again**. With ~40 Flutter plugin subprojects, parallel execution let Gradle snapshot `:app:stripDebugDebugSymbols`' output directory while AGP was still writing `libflutter.so` through a `.temp-stream-*` file:

```
Failed to create MD5 hash for file '...libflutter.so.temp-stream-f62fe5' as it does not exist.
```

The speedup is not worth a racy build. The reasoning is in a comment in `gradle.properties`.

## 6. What is needed before deploy

Ordered. Item 1 is a hard ordering constraint, not a preference.

1. **Apply the migration before deploying the API.**

   ```
   pnpm prisma:migrate:deploy
   ```

   `ProfileCompletionService.calculate()` now reads `profile_recommendation_dismissals` on a path that runs on **every wizard "Continue"**. Deploying the API against a database without that table fails completion for every member. Migration first, then the API.

2. **Run the integration suites against a disposable Neon branch** — set `INTEGRATION_DATABASE_URL` to a throwaway branch on a non-public schema. Never the primary database. These three suites are the only coverage that exercises the real write path for the DOB normalisation and onboarding changes.

3. **Merge to `main`.** Both commits and this session's work sit on `feat/manual-birthdate-entry`; a PR is still needed.

4. **Decide the `psychology` card's scoring.** It ships with `affectsScore: false` and carries no weight, pending approval. Until that decision it is offered but never counted.

5. **Member-visible score movement — needs a comms decision.** The re-based scoring means members who completed the psychology quiz (−3) or partner preferences (−5) will see their percentage *drop*, and members who answered every registration question will see it rise sharply from 20%. Nobody has been told this is coming.

6. **`DELETE /profiles/completion/dismissals/:cardKey` has no UI.** The endpoint exists and is tested, so a dismissal is provably reversible, but there is no "show my suggestions again" control. Worth adding to Settings before a member asks support to undo one.

7. **Regenerate the Prisma client** in any environment that does not run `postinstall` (`pnpm prisma:generate`).

## 7. Risks

- **The score change is visible and unexplained.** Item 5 above is the highest-impact risk in this report; it is a product/comms problem, not a technical one.
- **The completion hot path grew two queries.** Both are index-covered, but `calculate()` runs on every wizard step. Worth watching p95 on the draft endpoint after deploy.
- **`workIndustry` and `college` are new columns on a write path that already ships.** Older clients simply omit them; nothing stored is lost, and `education_details` is still populated for backward compatibility.
- **The build fix is machine-local in effect but repo-wide in configuration.** Anyone with a 4 GB-or-less machine may need to lower `org.gradle.jvmargs` locally; the setting is deliberately conservative at 4 GB rather than higher.
