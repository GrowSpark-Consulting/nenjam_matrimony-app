# Frontend → Backend Handoff

**Date:** 2026-07-29
**Branch:** `main`
**Frontend Version:** `1.0.0+1` (`Frontend/pubspec.yaml`)

---

## Overview

The Profile Drawer and every screen it can reach are now production-ready on the frontend. Concretely:

- Every Profile Drawer destination navigates to a real, working screen — no `Coming Soon` placeholders and no dead (`onTap: () {}`) taps remain anywhere in that navigation graph.
- Screens that already have a live backend endpoint (profile draft/completion, document verification status via `/profiles/draft`, account deletion, chat block/unblock) are fully wired to it — real loading, error, empty, and retry states throughout.
- Screens whose backend does **not** exist yet (Trust Score, Support Center, Privacy settings persistence) were built completely on the frontend — UI, forms, validation, providers, and repository **interfaces** — but deliberately stop short of calling a guessed-at endpoint. Each is backed by a small stub repository that reports "not implemented yet," surfaced as an honest unavailable/retry state. No fake data, no invented response shapes, no dead network calls anywhere.
- Several existing UI duplications were consolidated into shared widgets (`NmScoreRing`, `NmToggleRow`) while doing this work, rather than adding new one-off copies.
- Backend engineers can now implement the interfaces documented below and wire them into the existing (already-scaffolded, currently empty) NestJS modules — **no frontend changes should be required** to go live, provided response shapes match what's documented here.

This document was generated by inspecting the actual current state of both `Frontend/` and `backend/` — every status below reflects a file that was read directly, not an assumption.

## Backend Work Remaining

### Trust Score

**Frontend already contains:**
- Repository interface: `TrustScoreRepository.getMyTrustScore()` (`Frontend/lib/features/trust_score/domain/repositories/trust_score_repository.dart`)
- Stub implementation: `TrustScoreRepositoryUnavailable` — throws immediately, no network call (`.../data/repositories/trust_score_repository_unavailable.dart`)
- Provider: `trustScoreRepositoryProvider`, `myTrustScoreProvider` (`.../presentation/providers/trust_score_providers.dart`)
- Screen: `TrustScorePage` — animated ring (`NmScoreRing`), status item list (reuses `NmVerificationCard`), `NmShimmer` loading skeleton, `NmEmptyState` unavailable+retry error state, dark mode, pull-to-refresh

**Backend needs:**
- An endpoint — no path is defined yet on either side; suggest `GET /trust-score/me`, auth via the existing `FirebaseAuthGuard` pattern (same as every other authenticated route).
- **Response model** — see [Expected Response Models](#expected-response-models) below. Must include an overall score and a per-factor breakdown (icon/label/status) — the frontend model (`TrustScoreEntity`/`TrustItemEntity`, reused from `features/profile_detail`) expects `overallPercent: int` (0–100) and `items: [{label, status: verified|pending|incomplete}]`.
- **Already-real data to build from**: `User.trustScore: Int` (`@default(0)`) and `TrustScoreLog { delta, reason, newScore, createdAt }` (`backend/libs/database/prisma/schema.prisma:634-646`) already exist and are populated by `trust-score/listeners/trust-score.listeners.ts`. **Open question for backend**: is `User.trustScore` already on a 0–100 scale, or does it need normalizing before it maps to `overallPercent`? And should the "factors" list frontend expects be derived from recent `TrustScoreLog.reason` entries, or from a fixed set of checks (KYC/face/reports)? Neither is currently decided in code — please confirm before implementing.
- Error responses: standard 401 (unauthenticated) and 404/`204`-with-default-zero (no score yet) should both be handled — see [Error Handling Contract](#error-handling-contract).
- Authentication: same `FirebaseAuthGuard` as every other authenticated endpoint.
- Caching: no specific requirement from the frontend — `myTrustScoreProvider` is `autoDispose`, refetched on pull-to-refresh; a short server-side cache (score changes infrequently) would be reasonable but isn't required for correctness.

**Frontend contains:**

- `SupportTicketStatus` enum: `open | inProgress | resolved` — **note: backend's `SupportStatus` enum has a 4th value, `CLOSED`, that the frontend enum does not yet model — add `closed` to the Dart enum when wiring this up for real.**

- Stub implementation: `SupportRepositoryUnavailable` — throws immediately, no network call
- Providers: `supportRepositoryProvider`, `myTicketsProvider`
- Screens: `SupportTicketFormPage` (one reusable form for all four ticket types — subject + message fields, validation, loading, success/error dialogs), `TicketHistoryPage` (list, loading/empty/error/retry)

**Backend needs:**
- `POST` ticket submission — the backend already has scaffolded (empty) `TicketsController`/`CreateTicketDto`/`SupportTicketEntity`/`ticket.repository.ts`/`tickets.service.ts` under `backend/apps/api/src/modules/support/`. The Prisma `SupportTicket` table already exists: `{ id, userId, subject, body, status: SupportStatus, adminResponse, resolvedAt, createdAt, updatedAt }` (`schema.prisma:721-736`).
- **Naming mismatch to resolve**: the DB column is `body`, the frontend field is `message` — pick one name for the wire contract (recommend the DTO/response use `message` to match the frontend, translating to `body` internally, since the frontend is what many consumers will read).
- **Missing column**: there is no `type`/category column on `SupportTicket` today. The frontend needs to send/receive which of the four ticket types this is. Either add a `type` enum column, or agree that "type" is encoded into `subject`/not persisted server-side (not recommended — the Ticket History UI groups/labels by type).
- `GET` tickets (history) — paginate if ticket volume could grow per user; frontend doesn't currently send pagination params, so a simple "all of mine, newest first" response is sufficient to start, but design the response envelope so pagination can be added without a breaking change (e.g. wrap in `{ items: [...], nextCursor: ... }` rather than a bare array).
- Ticket statuses: `OPEN | IN_PROGRESS | RESOLVED | CLOSED` (backend enum) — frontend needs updating to add `CLOSED` once this is wired.
- Validation: non-empty subject and message (frontend already validates this client-side; backend should validate server-side too, standard defense-in-depth).
- Attachments: **not built on either side** — flagged only as a future consideration, not required for this handoff.

### Trust Score Algorithm

This is the one section requiring a genuine product/backend design decision, not just wiring:

- **Overall Score**: `User.trustScore` (Int, currently defaults to 0) is the presumed source. Confirm its scale (0–100 expected by the frontend) and whether it's already maintained correctly by `TrustScoreListeners`.
- **Factors**: the frontend's `TrustItemEntity` list (icon + label + status: `verified|pending|incomplete`) expects a breakdown, not just the single number. No current backend structure defines this breakdown explicitly — `TrustScoreLog.reason` is a free-text string per historical delta, not a stable "current factor" list. Recommend backend defines a small fixed set of factors (e.g. Mobile, Email, Aadhaar, Income, Asset, NRI, Face Match — mirroring the same 1:1 shape already used by `verificationBreakdown` on `/profiles/draft`) rather than trying to derive factors from the log table.
- **Weights**: not currently modeled anywhere; only needed if the frontend should show per-factor point values (it does not today — only a status chip per factor).
- **Messages/Recommendations**: not currently modeled or requested by the frontend UI; skip unless product wants to add this later.
- **Updated timestamp**: `TrustScoreLog.createdAt` gives a natural "last changed" timestamp; not currently surfaced in the frontend UI, but cheap to include in the response for future use.

## Delete Account

**Current frontend flow** (`Frontend/lib/features/settings/presentation/pages/settings_page.dart`):
1. User taps "Delete Account" → `AppDialogs.showDelete(...)` (reused existing destructive-confirm dialog component, not a new one-off).
2. On confirm → `AppDialogs.showProgress(...)` (non-dismissible spinner dialog) while awaiting the network call.
3. On success → dismiss progress dialog → `authRepositoryProvider.logout()` (same sign-out path the regular Logout flow uses, clearing local session/tokens) → `context.go(RouteNames.login)`.
4. On failure → dismiss progress dialog → `AppDialogs.showError(...)` with a generic retry-worthy message; **the account is not touched, nothing else changes**.
5. A `_deletingAccount` flag disables the row and shows an inline spinner for the duration, preventing double-taps.

**Expected backend behaviour** (already implemented, confirmed working): `DELETE /settings/delete-account` (`backend/apps/api/src/modules/settings/controllers/settings.controller.ts`) → `AccountDeletionService.deleteAccount(userId)` — deletes all DB rows, all uploaded storage objects, and the Firebase auth identity for that user.

- **Success response**: `204 No Content` (already implemented — `@HttpCode(HttpStatus.NO_CONTENT)`).
- **Failure response**: any non-2xx — frontend treats every failure identically (generic retry message); no special-casing per status code today.
- **Token invalidation**: once the Firebase identity is deleted server-side, the client's cached ID token becomes invalid; the frontend does not explicitly revoke it client-side beyond calling `logout()` immediately after a successful delete, which clears local session/prefs.
- **Logout**: always performed client-side immediately after a successful delete, regardless of whether the backend also invalidates the session — this is belt-and-suspenders and does not need backend coordination.

## Error Handling Contract

The frontend's general pattern (established by the existing `VerificationRepositoryImpl`/`SettingsRepositoryImpl` and followed by every new repository in this handoff): any non-2xx response is surfaced as a real `ApiException`/thrown error, propagated through Riverpod as an `AsyncError`, and rendered as an honest "unavailable" state with a Retry action — **never silently swallowed, never displayed as fake success or fake data.**

| Status | Frontend behavior |
|---|---|
| 400 | Shown as a validation/generic error — form screens (Support ticket) rely primarily on client-side validation already, but will surface a 400 the same as any other error if the backend rejects it |
| 401 | Handled globally by `AuthInterceptor` (`Frontend/lib/core/network/api_interceptor.dart`) — one silent token-refresh retry, then forces logout if still unauthorized. No per-screen handling needed. |
| 403 | Not specifically differentiated today — falls through to the generic error/retry state |
| 404 | Treated as "not available" — e.g. `VerificationStatusesController` explicitly catches this and treats it as "nothing submitted yet" rather than an error banner |
| 409 | Not currently differentiated — generic error/retry |
| 422 | Not currently differentiated — generic error/retry |
| 429 | Not currently differentiated — no client-side backoff/retry-after handling exists yet |
| 500 / 503 | Generic error/retry state, same as any other failure |

If backend developers need any of these to trigger distinct UI (e.g. a specific message for 429 rate-limiting on ticket submission), that is a frontend change to coordinate separately — flag it rather than assuming the generic handling is sufficient for a particular endpoint.

## Loading Behaviour

- **Loading (first load)**: `NmShimmer`-based skeletons sized to the real content's footprint (Trust Score ring, ticket history rows, privacy toggle rows) — never a bare spinner-only screen.
- **Refresh (pull-to-refresh)**: implemented via `RefreshIndicator` wrapping `ref.refresh(provider.future)` on every new screen (Trust Score, Privacy, Ticket History) — stale data stays visible under the refresh spinner rather than being cleared first (Riverpod's default `AsyncValue` `copyWithPrevious` behavior).
- **Retry**: every error state includes an explicit Retry action (`ref.invalidate(provider)` or equivalent) — no screen dead-ends on failure.
- **Offline / cached data**: no dedicated connectivity detection exists in this app; the above refresh/retry behavior is what stands in for "offline" handling — a failed refresh simply leaves the last-known-good data on screen with a retry affordance, rather than blanking the UI.

## Integration Notes

- **No fake frontend logic** — every "unavailable" screen (Trust Score, Support Center, Privacy save failures) is a real thrown error from a stub repository, not a hardcoded UI state. Wiring in a real implementation is the only thing needed to make the success path work; the loading/error/empty states already exist and don't need to change.
- **Repository interfaces already exist** for everything above — implement against them, don't redesign them without coordinating (changing a method signature or return type is a breaking change for the frontend).
- **Providers already exist** and are already wired into their screens — a backend engineer (or a frontend engineer swapping the stub) only needs to replace `TrustScoreRepositoryUnavailable`/`SupportRepositoryUnavailable` with a real Dio-backed class implementing the same interface, and register it in the corresponding `Provider<...>` definition.
- **Only API implementation is pending** for Trust Score, Support Center, and Privacy persistence — no frontend screens need to be built or redesigned once those endpoints exist.
- **Do not change response formats without coordinating** — several shapes above are marked `TODO(backend)` precisely because they are proposals, not confirmed contracts; changing field names/types after implementation will require a frontend follow-up.
- **Reused components**: this work deliberately reused rather than duplicated — `StepVerification` (verification UI), `conversationsNotifierProvider`/`NmInterestCard` (Blocked Profiles), `AppDialogs.showDelete/showProgress/showError/showSuccess` (all dialogs), `NmEmptyState` (all empty/unavailable states), `NmShimmer` (all loading skeletons), `SettingsRepository` (pre-existing, now actually wired to a provider).
- **New reusable widgets extracted**: `NmScoreRing` (`core/widgets/indicators/nm_score_ring.dart`) — replaced two separate near-duplicate private ring-gauge implementations in `identity_hero_card.dart` and `profile_performance_card.dart`, now used by both plus the new Trust Score page. `NmToggleRow` (`core/widgets/inputs/nm_toggle_row.dart`) — replaced Settings' twice-duplicated `ListTile`+`Switch` pattern, now used by Settings and Privacy.

- [ ] **Settings**: confirm Dark Mode requires no backend work (it doesn't); confirm Notifications toggle requires no backend work beyond existing FCM plumbing
- [ ] **Authentication**: every new endpoint should sit behind `FirebaseAuthGuard`, matching every existing authenticated route
- [ ] **Response validation**: confirm field names against the "Expected Response Models" section before shipping — several are marked as proposals, not confirmed contracts
- [ ] **Error handling**: confirm 401 triggers the existing global interceptor behavior correctly for each new endpoint (no special per-endpoint auth handling should be needed)
- [ ] **Pagination**: not required for v1 of Ticket History, but design the response envelope so it can be added later without a breaking change
- [ ] **Rate limiting**: not currently handled specially by the frontend (see Error Handling Contract, 429) — flag if any new endpoint needs client-side backoff behavior added
